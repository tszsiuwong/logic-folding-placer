# 从 DEF 到统计推断：一种分析 placer 行为的方法

## 我们做了什么事

在 gcd（301 实例）的 2D 和 3D placement 上，我们做了这样一组分析：

1. 从 2D/3D 两个 DEF 文件中读取每个单元的坐标，逐单元计算位移
2. 从 Verilog 中提取网表拓扑，结合 DEF 坐标计算每条网线在 2D 和 3D 中的 HPWL
3. 对 265 条网线的 2D/3D HPWL 比值做分桶统计和假设检验
4. 从 `dbl_custom_write` 输出中提取 221 个 HBT 坐标，做基于网格的溢流分析
5. 用递归谱分割从网表中估计 Rent 指数

全部分析用 Python 完成，总耗时约 30 秒（不含 placement 运行时间）。

## 得到的结果

| 分析项 | 结果 |
|--------|------|
| 3D/2D 全局 HPWL | 79% |
| 逐线统计 | 129 变短，134 变长（50/50） |
| Spearman ρ（线长 vs 比值） | −0.64（p = 5×10⁻³²） |
| 显著收益阈值 | 20µm（p<0.001） |
| 过渡带 | 10–20µm（p=0.106，不显著） |
| 2D→3D 位移 | 均值 47.4µm，与离中心距离 r=0.919 |
| 同/跨 Die 邻居 2D 距离 | 均为 41µm |
| HBT 溢流（1.5µm pitch） | 11% bin 超限，最大 2× 容量 |
| Rent p | 0.698 |

## 为什么这种分析在过去不常见

**所有输入数据都是 placer 的标准输出。** DEF、Verilog、log——这些文件在任何一个数字后端流程中都存在。做上述分析不需要修改任何 EDA 工具代码，使用的是工具已有的输出文件。

但传统流程中，这些文件承担的角色不是"分析数据"而是"流程载体"：DEF 是给下一个工具（布线器、提取器）的输入，log 是人肉检查的对象。没人把它们当成可编程访问的结构化数据。

如果要用传统 Tcl 脚本实现同样的分析，需要逐网线调用 `report_net`、逐单元调用 `get_property`，对 265 条网线和 301 个单元做双重循环。在商用工具的 Tcl 接口上，这不仅是工作量大——Tcl 的对象查询本身就是高延迟操作，265×2 次调用可能就需要数十分钟。而对于更大的设计（如 128K 实例的 ariane133），这个时间会变得不可承受。

当 DEF 坐标和 Verilog 拓扑被视为可以通过 Python 直接读写的结构化数据时，分析所依赖的方法（t-test、Spearman、KDTree、谱分割等）与 EDA 领域无关，而与统计和数据结构有关。这是视角的切换，不是工具能力的升级。

## 方法的一般性

上述分析没有用到 gcd 特有的任何性质。理论上，同样的流程可以应用于其他有 DEF + Verilog 输出的设计。但在更大设计（jpeg 23K 实例、ariane133 128K 实例）上尚未验证，解析和统计计算的实际性能有待测试。

## 前提

这个方法依赖 placer 输出以下数据：

| 数据 | 格式 | 说明 |
|------|------|------|
| 2D/3D 单元坐标 | DEF COMPONENTS | 任何 placer 的标准输出 |
| 网表拓扑 | Verilog | 综合后的门级网表 |
| Tier 指派 | partition sidecar / 3D DEF cell type 后缀 | heteroplace3d 输出 |
| HBT 坐标 | dbl_custom_write Terminal | 需要工具侧支持 |
| 单元尺寸 | DBL LibCell / LEF MACRO | pin offset 可选 |

前两项是大多数数字后端流程的输出。后三项来自 heteroplace3d——对不同的 placer，数据提取方式需要相应调整。

## 与 agentic_tao_physical_design_flow 的对齐

[agentic_tao_physical_design_flow](https://github.com/tszsiuwong/agentic_circuit_optimizer/blob/main/agentic_tao_physical_design_flow.md) 描述了 TAO 物理设计流程的概念框架。以下是本次 gcd 实验与该文档中几个判断的关系。

### 1. §3.1 观测粒度失配 — 一个低保真原型

该文档指出了批处理模型对 Agent 的致命伤：

> 智能体的一次变异假设常是单元/路径级的，批处理工具只接受全局重跑。全设计文本报告要智能体自己 grep，脆弱且丢失结构。

本次实验中，我们没有依赖 placer 的报告，而是从 DEF、Verilog、partition 文件中直接读取坐标和拓扑，逐网线、逐单元地计算了 2D/3D 对比。但这远非"解决"——这只是在 gcd 上走通了一条分析路径。关键差距在于：

- **我们在 placement 完成后做静态分析，而非在 placement 过程中做增量观测。** §3.1 说的是"看着它跑歪了及时纠正"，我们做的是"跑完了回过头看"。
- **数据从 DEF/Verilog 提取依赖实例名匹配。** 在当前实验中匹配率 100%，但当综合工具重命名或打平层次后，这个匹配率会下降。
- **没有时序信息。** 观测粒度在几何（HPWL）层面达到了细粒度，但在时序（slack、path delay）层面仍为零。

### 2. §3.2 查询即报告 — 静态文件上的结构化查询

该文档设想：

> 查询即报告：`query_paths(slack<0, through_tier_crossing=True)` 返回结构化记录，不是文本文件。

本次实验中虽然没有时序数据，但在几何层面实现了类似的能力。Agent 在 DEF/Verilog/partition 三个文件上做 join 查询：

- "哪些网线在 3D 中比 2D 长？"
- "20µm 以上的网线是否显著受益？"
- "同 Die 的邻居在 2D 上比其他邻居更近吗？"

查询的数据源是 placer 的最终输出文件，不是 placer 内部数据库。这意味着查询只能在 placement 完成后进行，不能在中途干预。离 §3.2 设想的"事务级变异 API + 增量传感器"还有本质距离。

### 3. §1.2 细粒度逻辑折叠 — 在两个指标上做了量化

该文档的核心物理假设：

> 组合逻辑必须被切分为跨层分布的分段，而分割方案的质量直接决定最终 PPA。

本次实验中观察到的两个现象与该假设一致：

- 分割效果因线长而异：20µm 以上的线 90% 受益，5µm 以下的线 86% 受损。
- placer 的层指派与 2D 空间邻近性无关：同/跨 Die 邻居在 2D 上的原始距离均为 41µm。

如果分割方案是 placer 内生的、且 placer 没有选择性，那么分割质量的好坏取决于线本身的长度分布。单靠 placer 无法保证"把该切的线切对"——这指向了 Agent 介入的一个可能方向。

### 4. §3.3 单一真源 — 文件级 join 的局部验证

该文档设想了一个统一数据库容纳逻辑、物理、层指派、约束与度量。本次实验中，我们用三个独立文件拼出了一个功能等价物：

| 文件 | 提供的信息 |
|------|-----------|
| DEF（2D + 3D） | 单元坐标、物理位置 |
| Verilog | 网表拓扑、逻辑连接 |
| DBL / partition | 单元尺寸、层指派 |

在同一个 Python 进程中 join 这三个文件，可以支持跨文件查询（"从 Verilog 找网线成员 → 从 DEF 查坐标 → 从 partition 对层指派"）。通过实例名 join 的覆盖率在当前实验中是 100%（301/301）。

但这个"统一数据库"极其脆弱：三个文件的 ID 一致性依赖于工具的命名保真度，没有任何机制保证跨文件的一致性。一旦综合工具重命名或打平层次，join 就会断裂。§3.3 主张的单一真源正是为了解决这个问题——我们目前的文件级 join 只能说明这个方向值得做，远未达到工程可用。

### 整体判断

该文档在 2025 年写下 §3.1–§3.2 时，这些"理想工具接口"是概念层面的设计蓝图。本次 gcd 实验在一个极小的设计（301 实例）上，用文件级解析的方式，为其中几个能力提供了数据层面的实例。离文档设想的完整形态（事务级变异 API、增量传感器、统一数据库）仍有距离，但这条路径在极小规模上是走得通的。

### 边界与局限

上述分析全部在**门级网表**层面进行，本质是对 placer 行为的描述性分析——更精确地回答"发生了什么"，但无法回答"应该怎么做"。

架构师决定"模块 A 和 B 必须在同一层"，这个决定的物理后果（对 HPWL、对 HBT 密度、对位移分布）可以通过后端分析量化。但**后端分析不能产生这个决定**——它只能校验和反馈。20µm 阈值是统计规律，但哪条具体的 25µm 线是控制通路的关键路径、哪条只是不重要的长绕线——这个区分只有架构师能做。

本文档描述的方法，是把后端的仪表盘擦得更亮。但仪表盘连着的那台机器——架构假设 → 物理实现 → 数据反馈 → 修正假设的闭环——还没有运转。没有架构师的迭代，后端分析的天花板就是更精确的 placer 行为描述，不是更好的设计。
