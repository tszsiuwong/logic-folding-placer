# 从 DEF 到统计推断：一种分析 placer 行为的方法

## 我们做了什么事

在 gcd（301 实例）的 2D 和 3D placement 上，我们做了这样一组分析：

1. 从 2D/3D 两个 DEF 文件中读取每个单元的坐标，逐单元计算位移
2. 从 Verilog 中提取网表拓扑，结合 DEF 坐标计算每条网线在 2D 和 3D 中的 HPWL
3. 对 265 条网线的 2D/3D HPWL 比值做分桶统计和假设检验
4. 从 `dbl_custom_write` 输出中提取 221 个 HBT 坐标，做基于网格的溢流分析
5. 用递归谱分割从网表中估计 Rent 指数

全部分析用 Python 完成，总耗时约 30 秒（不含 placement 运行时间）。

## 得到的结果

| 分析项 | 结果 |
|--------|------|
| 3D/2D 全局 HPWL | 79% |
| 逐线统计 | 129 变短，134 变长（50/50） |
| Spearman ρ（线长 vs 比值） | −0.64（p = 5×10⁻³²） |
| 显著收益阈值 | 20µm（p<0.001） |
| 过渡带 | 10–20µm（p=0.106，不显著） |
| 2D→3D 位移 | 均值 47.4µm，与离中心距离 r=0.919 |
| 同/跨 Die 邻居 2D 距离 | 均为 41µm |
| HBT 溢流（1.5µm pitch） | 11% bin 超限，最大 2× 容量 |
| Rent p | 0.698 |

## 为什么这种分析在过去不常见

**所有输入数据都是 placer 的标准输出。** DEF、Verilog、log——这些文件在任何一个数字后端流程中都存在。做上述分析不需要修改任何 EDA 工具。

但传统流程中，这些文件承担的角色不是"分析数据"而是"流程载体"：DEF 是给下一个工具（布线器、提取器）的输入，log 是人肉检查的对象。没人把它们当成可编程访问的结构化数据。

如果要用传统 Tcl 脚本实现同样的分析，需要逐网线调用 `report_net`、逐单元调用 `get_property`，对 265 条网线和 301 个单元做双重循环。在商用工具的 Tcl 接口上，这不仅是工作量大——Tcl 的对象查询本身就是高延迟操作，265×2 次调用可能就需要数十分钟。而对于更大的设计（如 128K 实例的 ariane133），这个时间会变得不可承受。

**Agent 改变的不是工具能力，是对"什么是数据"的假设。** 当 DEF 坐标和 Verilog 拓扑被视为可以通过 Python 直接读写的结构化数据时，分析就从"工具支持什么"变成了"你想到什么统计方法"。t-test、Spearman、KDTree、谱分割——这些方法跟 EDA 无关，只跟数据和问题有关。

## 方法的一般性

上述分析中没有一步依赖于 gcd 的特殊性质。同样的 Python 脚本可以直接用于任何有 DEF + Verilog 输出的设计。对更大的 benchmark（jpeg 23K 实例、ariane133 128K 实例），唯一的变化是运行时间——统计方法的复杂度是 O(n log n) 级别的，足够应对百万级实例。

## 前提

这个方法依赖 placer 输出以下数据：

| 数据 | 格式 | 说明 |
|------|------|------|
| 2D/3D 单元坐标 | DEF COMPONENTS | 任何 placer 的标准输出 |
| 网表拓扑 | Verilog | 综合后的门级网表 |
| Tier 指派 | partition sidecar / 3D DEF cell type 后缀 | heteroplace3d 输出 |
| HBT 坐标 | dbl_custom_write Terminal | 需要工具侧支持 |
| 单元尺寸 | DBL LibCell / LEF MACRO | pin offset 可选 |

其中前两项是任何数字后端流程的标配。后三项是 heteroplace3d 特有的，但不影响方法的一般性——如果换一个工具，只需要调整数据提取的格式适配。
